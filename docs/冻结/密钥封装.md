# 冻结：设备内密钥封装

> 状态：设备侧实现与本文一致；**尚无真机证据**。格式版本 v1。
> 关键约束：这一层只保护设备内的私钥副本，**不改变业务派生**（需求 §2）。

## 1. 业务封装 v1

私钥在设备内以版本化认证加密封装保存。派生链：

```
KEK  = PBKDF2-HMAC-SHA256( UTF8(PIN), salt = salt16, iters = 120000, 32B )
KEK' = HKDF-SHA256( ikm = KEK, salt = deviceSecret32, info = "rockey:vault:v1", 32B )
ct,tag = AES-256-GCM( KEK', nonce12, AAD, priv32 )
```

记录 payload（110 字节，紧随 `store::WriteRecord` 的 18 字节记录头）：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 33 | 压缩公钥 |
| 33 | 16 | KDF 盐（随机） |
| 49 | 12 | GCM nonce（随机） |
| 61 | 32 | 密文 |
| 93 | 16 | GCM tag |
| 109 | 1 | PIN 位数 |

`AAD`（前缀 `"rockey:vault:v1|"`，共 15 + 1 + 4 + 33 + 1 = 54 字节）：

```
"rockey:vault:v1|" || envelopeVersion(u8) || generation(u32 big-endian)
                  || pubkey(33) || pinDigits(u8)
```

公钥与 PIN 位数进 AAD，所以攻击者既不能把封装换到别的公钥上，
也不能改 PIN 位数后再拿原 PIN 去解。generation 进 AAD，
使旧 generation 的密文无法在新记录上重放。

`deviceSecret32` 单独存一份文件：只拿到 flash 也解不开封装
（**但这仍不是安全芯片级别的保护**，见硬件清单「安全功能现状」）。

## 2. PIN 失败计数与递增等待

状态记录 `/vault/state.bin`，12 字节 payload：

| 偏移 | 长度 | 内容 |
| --- | --- | --- |
| 0 | 4 | `failCount` (u32) |
| 4 | 4 | `waitRemainingMs` (u32) |
| 8 | 2 | `paramsVersion` = 2 |
| 10 | 2 | 保留 |

等待时长：`ROCKEY_PIN_FAIL_BASE_MS` (2s) 指数翻倍，封顶
`ROCKEY_PIN_FAIL_CAP_MS` (10min)。

**为什么落盘的是时长而不是时间戳**：设备没有可信时钟，`millis()` 每次上电从 0
开始。如果落盘上次运行的 `millis()`，`now - lastFail` 会回绕成一个巨大值，
于是每次重启都把未完成的等待直接抹掉 —— 那正是需求 §3 明令禁止的
「拔线恢复无限快速尝试」。现在的做法是：

- 落盘 `waitRemainingMs`（本次失败要求等待的完整时长）与 `failCount`；
- 等待进度在 RAM 里按本次启动的 `millis()` 推进；
- 重启后从完整剩余时长重新计 —— 方向是保守的，绝不因此缩短或取消等待；
- 失败计数继续递增，所以反复拔电只会让等待越来越长。

`paramsVersion` 不等于 2 时按「旧格式的第二个字段是时间戳」处理：
保留 `failCount`，把等待重置为**该计数的完整时长**，取更保守的一侧。

未设自动擦除阈值（`ROCKEY_PIN_FAIL_WIPE_THRESHOLD = 0`，需求 §3）。
失败计数本身在 MCU 上可被物理绕过，**不得宣传成 Secure Element 等级**。

## 3. 密码学实现现状（已修正）

以下两处曾经是"实现完全错误但自检显示通过"，第二轮已修正并加了对照测试：

| 组件 | 原问题 | 现状 |
| --- | --- | --- |
| `crypto/ripemd160.cpp` | 右线移位表误填成 RIPEMD-128 的表 → 所有 HASH160 与地址都错 | 改用 ESP-IDF 自带的 mbedTLS RIPEMD-160；`SelfTest()` 执行 7 条官方向量 + 100 万个 'a' |
| `crypto/aead.cpp` | 解密方向把 GHASH 算在明文上 → **解封/解本地秘密/解任何加密帧全部失败** | 按方向取密文进 GHASH；`SelfTest()` 改为与 mbedTLS GCM 对齐的 AES-256 向量 |
| `crypto/aead.cpp` 的 `SelfTest()` | 拿 AES-256 的输出比 NIST 的 AES-128 用例 → 每次上电误报失败 | 覆盖空明文 / 整块 / 带尾零头 / 带 AAD，以及往返与篡改拒绝 |
| `crypto/digest.cpp` 的 `HkdfSha256` | expand 阶段从未用 PRK 初始化 HMAC → **输出只取决于 info** | 改用 mbedTLS HKDF；见下 |
| `crypto/x25519.cpp` | 模数 2^255-1、u 坐标大端读、ladder 初值写反；低阶点输出未求逆的 x2 | 按 RFC 7748 重写，无穷远点输出全零并拒绝 |

### HKDF：这一条曾让 PIN 保护完全失效

`KEK' = HKDF(ikm = KEK, salt = deviceSecret, info)` 里，HKDF 的 expand
从未用 PRK 做过 HMAC 初始化，于是 `KEK'` 与 KEK、deviceSecret 都无关，
是一个公开常量。后果：

- **任意同位数 PIN 都能解封**（KEK 变了，KEK' 不变）；
- 本地秘密 v3 的派生密钥与业务私钥无关 —— 任何人都能解开别人的本地秘密；
- 链路 c2s/s2c 密钥与 X25519 共享秘密无关 —— 加密通道不提供机密性。

现在由 `tests/host/test_digest.cpp` 固定四条性质：RFC 5869 A.1/A.3/A.4 逐字节一致、
与 `mbedtls_hkdf` 随机对照一致、**改 ikm/salt/info 必须改输出**、
以及封装派生链「同位数错误 PIN 不得得到同一密钥」。

对照测试：`tests/host/test_aead.cpp` 把 `aead.cpp` 与 `mbedtls_gcm` 在
10 × 10 组长度矩阵上逐字节比对（含改密文 / 改 tag / 改 AAD / 换 key / 换 nonce
五类拒绝）。

## 4. 原子提交与断电

`store::WriteRecord` 走「临时文件 → rename」单一提交点，rename 之前旧记录保持
有效；记录头带单调递增的 generation，读旧记录即得下一代号；读取时校验 CRC，
损坏即视为不存在。

这条路径上每个提交点都需要按 RK-07 做断电故障注入 —— **尚未执行**。

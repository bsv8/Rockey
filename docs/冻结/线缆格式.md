# 冻结：线缆格式与字段表

> 状态：设备侧实现已按本文固定；Keymaster 侧尚未对接。
> 本文是协议草案 §9「规范编码冻结项」的落地，是 `docs/冻结/` 系列的第一份。
> **编码规则与字段名长度都是接口的一部分**：改这里等于改 wire 版本。
> 2026-10-09 收窄：`evidence.receive`（信用/证据服务入口）与外部正文（Markdown）
> 接入已撤销，本文相应行删除而不是留空实现；`tx.feepool-sign` 登记为
> **已知但当前不可用**，其字段表在脚本/阶段冻结前不存在（不得套用 P2PKH 字段）。

## 1. 为什么编码顺序是接口

设备内的 CBOR 读写器强制 RFC 8949 确定性编码的一个变体：

- 整数一律最短表示（`0x17` 不写成 `0x18 0x17`）；
- **map 的键按「字节长度优先，再字节序」严格递增**，重复键、乱序键一律失败；
- 嵌套深度 ≤ 6，键名 ≤ 32 字节，字节串/文本长度不得超过所在缓冲剩余字节。

这不是洁癖。设备侧 `Writer::Key()` 一旦看到乱序就把 `ok()` 置假，调用方返回
`false` 且**不发任何帧** —— 表现为主机侧死等，而不是一个明确的错误码。
`tools/wire-encoding/main.py` 在构建前静态拦住这类错误，
`tests/host/test_proto.cpp` 用正反向向量验证读写器本身。

Keymaster 侧必须用同样的规则编码，否则设备会静默拒绝。

## 2. 帧层

```
0  magic0 = 0xA5
1  magic1 = 0x5A
2  version = 1
3  type(1)
4  flags(1)
5  seq(4, little endian)
9  payloadLen(2, little endian) <= ROCKEY_MAX_FRAME_PAYLOAD (1536)
11 payload
11+len crc32(4, little endian，覆盖 [2, 11+len))
```

| type | 值 | 加密 | 方向 |
| --- | --- | --- | --- |
| `HELLO` | 0x01 | 否 | 主机 → 设备 |
| `HELLO_ACK` | 0x02 | 否 | 设备 → 主机 |
| `PAIR_CONFIRM` | 0x03 | 是 | 主机 → 设备 |
| `PAIR_OK` | 0x04 | 是 | 设备 → 主机 |
| `PROVE_POSSESSION` | 0x05 | 是 | 主机 → 设备 |
| `PROVE_OK` | 0x06 | 是 | 设备 → 主机 |
| `REQUEST` | 0x10 | 是 | 主机 → 设备 |
| `RESPONSE` | 0x11 | 是 | 设备 → 主机 |
| `EVENT` | 0x12 | 是 | 设备 → 主机 |
| `PING` / `PONG` | 0x20 / 0x21 | 是 | 双向 |
| `ABORT` | 0x30 | 是 | 双向 |

`flags`：`0x01 ACK_REQUIRED`、`0x02 CANCEL`。`CANCEL` 走取消通道，设备只保证
「尚未执行的请求确实没执行」，已交付的签名不承诺撤回。

## 3. 握手

1. 主机 → `HELLO`，键序：
   `hostEph(7) < hostNonce(9) < capabilities(12) < runGeneration(13) <
   protocolVersion(15) < walletGeneration(16) < backendGeneration(17)`
   未知键一律拒绝；`protocolVersion` 不等于 1 时设备关闭链路，不隐式降级。
2. 设备派生方向分离密钥：
   `c2s key/nonce = HKDF-SHA256(shared, salt=transcript, info="rockey:link:c2s:key:v1" / ":nonce:v1")`，
   `s2c` 同理用 `"rockey:link:s2c:..."`。**两个方向不得共用同一把密钥或同一条 nonce 链。**
   `transcript = SHA256("rockey:handshake:v1" || 版本 || 主机nonce || 设备nonce ||
   主机eph || 设备eph || deviceRunId || 主机三个世代 || 公钥)`
3. 设备 → `HELLO_ACK`，键序：
   `state(5) < language(8) < deviceEph(9) < publicKey(9) < deviceNonce(11) <
   deviceRunId(11) < capabilities(12) < firmwareBuildId(15) <
   pairingRequired(15) < protocolVersion(15) < supportsLockedInfo(18)`
4. 设备屏幕显示配对码 =
   `SHA256("rockey:link:pairing:v1" || transcript)` 前 3 字节 → 6 位十进制。
   用户在设备上实体确认后，主机才发 `PAIR_CONFIRM`。
5. 配对码一致 → 设备回 `PAIR_OK`，进入已加密状态。
6. 主机 → `PROVE_POSSESSION {challenge}`；设备用业务 Key 对 challenge 签名，
   回 `PROVE_OK`（键序 `challenge(9) < publicKey(9) < sessionId(9) < signature(9) <
   sessionEpoch(12)`），**并在此刻开启会话**。
   未通过持有权证明之前，设备不接受任何 `REQUEST`。

## 4. 请求信封

键序：

```
body(4) < requestId(9) = sessionId(9) = walletGen(9)
     < backendGen(10) = commitment(10) < sessionEpoch(12) < runGeneration(13)
```

- `commitment` 是 32 字节请求承诺，**必填**；缺失或全零一律 `invalid-request`。
  早先它被复制进队列后从不校验，缺失还按全零接受，等于"不承诺也能执行"。
- 设备校验：承诺非全零；会话已开、`sessionEpoch` 一致、三个主机世代与开启会话时**完全相同**。
  主机不能中途改写世代来复用已开的授权窗口。
- 承诺的前 16 字节进入 `policy::MatchKey`，因此持续授权只覆盖被承诺过的那个请求；
  换一个承诺就是另一个授权。

## 5. 操作请求体

顶层键序：`op(2) < opVersion(9) < <该操作自己的字段>`。
`op` 必须是第一个键（长度 2 最小），未知字段一律拒绝 —— 不允许夹带降级字段。

| 操作 | 字段（括号内为键名字节长度） |
| --- | --- |
| `identity.prove` / `identity.authorize` | `challenge(9)`, `purpose(7)` |
| `tx.p2pkh-sign` | `inputIndex(10)`, `network(7)`, `prevouts(8)`, `rawTx(5)` |
| `tx.p2pkh-sign` 的 `prevouts` 元素 | `txid(4)`, `vout(4)`, `proven(6)`, `script(6)`, `satoshis(8)` |
| `tx.feepool-sign` | **无字段表**：已登记 op 名，但设备在冻结前直接拒绝（`unsupported`），不解析任何字段 |
| `channel.public-message` / `hash-request` / `private-message` | `challenge(9)`, `message(7)`, `protocol(8)` |
| `channel.seal` | `message(7)`, `nonce(5)`, `protocol(8)`, `recipientPub(12)` |
| `channel.open` | `nonce(5)`, `protocol(8)`, `senderPub(9)`, `sealed(6)` |
| `secret.seal` | `plaintext(9)`, `scope(5)` |
| `secret.open` | `sealed(6)`, `scope(5)` |
| `secret.open` 的 `sealed` 元素 | `ciphertextHex(13)`, `keySource(9)`, `nonceHex(8)`, `saltHex(7)`, `version(7)` |
| `content.attest-digest` | `digestHex(9)`, `fileName(8)`, `purpose(7)` |

文本字段（`purpose` / `protocol` / `scope` / `fileName`）进评审文档前必须经过
UTF-8 清洗、长度上限（`ROCKEY_MAX_DYNAMIC_TEXT`）与缺字检测；无法解释的字节
按 malformed 拒绝，缺字在阅读页脚显示码点。**外部正文整章不进设备** ——
信用长文与 Markdown 由 Keymaster 展示，不占用设备帧容量与字库预算。

`tx.p2pkh-sign` 的 `rawTx` 上限 = `ROCKEY_MAX_PLAINTEXT - 384`（1016 字节），
因为请求信封与 `prevouts` 证据共用同一条加密帧。更大的交易需要**有界分片传输**，
该规则尚未冻结，因此当前明确不可用（拒绝而不是宣称支持）。

## 6. 响应

`RESPONSE` 信封键序：`payload(7) < requestId(9)`。`payload` 是下面各表的字节串。

| 操作 | 响应键序 |
| --- | --- |
| `identity.prove` / `authorize` | `challenge(9)`, `publicKey(9)`, `signature(9)`, `signatureFormat(25)` |
| `tx.p2pkh-sign` | `sighash(7)`, `publicKey(9)`, `signature(9)`, `sighashType(11)` |
| `content.attest-digest` | `publicKey(9)`, `signature(9)`, `statementDigest(15)` |
| `channel.public-message` | `publicKey(9)`, `signature(9)` |
| `channel.hash-request` | `requestDigest(13)`, `signature(9)` |
| `channel.private-message` | `publicKey(9)`, `signature(9)`, `messageDigest(13)` |
| `channel.seal` | `nonce(5)`, `sealed(6)`（`sealed` = 密文 ‖ tag） |
| `channel.open` | `plaintext(9)` |
| `secret.seal` | `saltHex(7)`, `version(7)`, `nonceHex(8)`, `keySource(9)`, `ciphertextHex(13)` |
| `secret.open` | `plaintext(9)` |
| `migration.status` | `record(6)` |

错误码即 `ops::ErrorCode` 的枚举值（`ops/dispatch.h`）。

## 7. 签名一律域隔离

设备**不存在**"签任意 32 字节"的接口。每种签名签的都是设备自己构造的、
带域标签的摘要，主机提供的原始字节只作为**输入材料**出现：

| 操作 | 被签摘要 |
| --- | --- |
| `identity.prove` | `SHA256d("rockey:identity:prove:v1" \| 0x00 \| pubkey(33) \| sessionId(u32be) \| sessionEpoch(u8) \| challenge(32) \| 0x00 \| purpose)` |
| `identity.authorize` | 同上，域标签为 `rockey:identity:authorize:v1` |
| `PROVE_OK`（持有权证明） | `SHA256d("rockey:link:possession:v1" \| 0x00 \| pubkey(33) \| deviceRunId(u32be) \| hostRunGeneration(u32be) \| sessionId(u32be) \| challenge(32))` |
| `tx.p2pkh-sign` | 设备自算的 BSV sighash |
| `content.attest-digest` | `SHA256d("rockey:content:v1" \| 0x00 \| purpose \| 0x00 \| digestHex)` |
| `channel.public-message` | `SHA256d("rockey:channel:public:v1" \| 0x00 \| protocol \| 0x00 \| message)` |
| `channel.hash-request` | `SHA256d("rockey:channel:hash:v1" \| 0x00 \| protocol \| 0x00 \| challenge)` |
| `channel.private-message` | `SHA256d("rockey:channel:private:v1" \| 0x00 \| protocol \| 0x00 \| message)` |

**为什么必须这样**：如果设备直接签主机给的 32 字节 challenge，就把交易摘要
当 challenge 塞进来即可换走一个与 `tx.p2pkh-sign` 同等有效的交易签名，
而这笔交易从没在设备屏幕上出现过。域隔离让这类跨操作复用不可能成立。
主机可以自行重算上表中的摘要并验签；`PROVE_OK` 会把 `statementDigest`
一并返回。

## 8. 持续授权的匹配键

授权绑定（`policy::MatchKey`）：业务 Key、设备运行、连接、App 会话、
`sessionEpoch`、主机三个世代、operation id、**protocol**、**direction**、
以及**设备自算的对象摘要**（不是消息原文）。

- `protocol` 由已登记的协议名确定性地映射到一字节；未登记的协议直接拒绝，
  不会退化成"无协议"。
- `direction`：`channel.seal` 为 outbound，其余 channel 操作为 inbound。
- 对象摘要：
  - identity = `SHA256("rockey:identity:v1" \| 0 \| challenge \| 0 \| purpose)`
  - channel public/hash/private = `SHA256("rockey:channel:v1" \| 0 \| protocol \| 0 \| peer33 \| 设备自算的消息摘要)`
  - channel **seal** = 上面同式，但摘要对象是**明文**（seal 请求没有 ciphertext，
    按密文取会让每个合法请求都变成 malformed）
  - channel **open** = 同式，摘要对象是**密文**
  - local secret = `SHA256("rockey:localsecret:v1" \| 0 \| scope \| 0 \| 密文或明文摘要)`
  - transaction = sighash 的前 16 字节
- `commitment`：主机请求承诺的前 16 字节

对端公钥按方向校验：`channel.seal` 只接受 `recipientPub`，
`channel.open` 只接受 `senderPub`；交叉填写直接拒绝，
否则授权会落到错误的对手方上。

因此"允许 A 的这一条消息"不会外溢到 A 的其它消息、不会外溢到 B、
也不会外溢到另一个协议或另一个方向。

## 9. 尚未冻结 / 尚未对接

以下项本文没有固定，Keymaster 现在不要依赖：

- 设备事件（`EVENT`）的负载结构 —— 设备侧已能发出 `deviceState` / `sessionId`，
  但完整的请求状态、授权变更与锁定事件尚未定义。
- **Channel seal/open 的密钥协商**：设备侧已改成确定性的 X25519 静态-静态
  ECDH（此前每次随机派生临时密钥且不回传公钥，seal/open 无法闭环）。
  具体派生规则见 `src/ops/dispatch.cpp` 的 `ChannelX25519Priv` /
  `ChannelPeerPoint` / `ChannelSealKey`，**尚未与 Keymaster 的 Channel 协议
  对齐**；对齐前不得据此声称软端↔硬端互通（协议草案 §5）。
- **费用池（`tx.feepool-sign`）**：op 名已登记但**当前不可用**。开池/funding、
  更新累计付款、关闭/结算、退款各阶段的真实脚本、双方公钥顺序、
  sequence/locktime、状态证据与授权规则未冻结；在此之前设备不解析任何字段，
  也不接受把池交易伪装成 `tx.p2pkh-sign`（池脚本在这里一律按未知脚本拒绝，
  有主机侧负向测试固定该行为）。
- **有界分片传输**：超过单帧容量的交易无法送达，分片规则未冻结前不支持。
- 迁移（`migration.import` / `export`）与恢复备份的 wire 结构。
- 操作请求中 `requestCommitment` 的**覆盖规则**（哪些字段进承诺、怎么编码）。
  设备当前做到的是：缺失或全零一律拒绝，且承诺并入授权匹配键 ——
  一条持续授权只对它被承诺过的那一个请求有效。真正的"覆盖实际对象/范围/
  证据与显示内容"要等两端冻结编码后由设备重算比对。

已撤销（不再作为接口维护，也不复用其编号）：`evidence.receive` 及其
`invalid-evidence(7)` 错误码、外部正文（Markdown）续传、设备侧信用信任根。

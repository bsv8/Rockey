## 1. 目标与非目标

**目标**

| 编号 | 目标 |
| --- | --- |
| G1 | **多屏**：ILI9341 / ST7789 / … **编译期单选**，不做运行时驱动表 |
| G2 | **多板**：芯片、引脚、屏幕几何、布局参数可换 |
| G3 | **多按键映射**：按键的"电平来源"可换（GPIO / 虚拟 / 主机），状态机不动 |
| G4 | **虚拟屏是一等公民**：裸板上没有物理屏，屏由我们自己的驱动映射到 Web |
| G5 | **零硬件冗余**：没选中的驱动、没启用的后端，不进二进制 |

**非目标**

- 不做运行时热插拔面板/驱动表（嵌入式上没有意义，且要背全部驱动的 flash）。
- 不用虚拟屏替代真机 LCD / 背光 / 电气 / 观感验收（边界与 `font-render-test/README.md` 一致）。
- 不把调试台开放成正常钱包 RPC（沿用 `DevTestControl` 的既有口径与 `rockey_config.h` 的互斥门禁）。

## 2. 现状：耦合点（已核实）

| 位置 | 硬件耦合 | 规模 |
| --- | --- | --- |
| `src/board/display.cpp` | **全仓库唯一的 `TFT_eSPI tft;`**，所有面板 I/O | 258 行 |
| `src/board/buttons.cpp` | **唯一一行硬件读取**：`kPin[3] = {Board::kPinBtnA/B/C}` + `pinMode(INPUT_PULLUP)` + `digitalRead(...) != LOW` | 1 处，其余是纯状态机 |
| `src/board/buttons.h` | `#if ROCKEY_DEV_BUTTON_API` 的注入字段 `testDown_/testUntil_` + `DevSetLevel()` | 焊接在状态机里 |
| `src/board/board.h` | 引脚、320×240、旋转、`kHeaderH/kFooterH/kContentY/H` | 单个 constexpr struct |
| `include/User_Setup.h` | TFT_eSPI 编译期宏，经 `-include` 前置到每个 TU | 1 文件 |
| `src/core/rockey_config.h` | 已有互斥门禁模板（`ROCKEY_DEV_BUTTON_API && ROCKEY_BUILD_RELEASE → #error`） | 可复用 |

三个关键结论：

1. **两个适配层的缝都已经存在，且都很薄**：`Display` 是静态门面（`ui/widgets.cpp` 366 行完全不碰 TFT_eSPI）；`Buttons` 除了一行 `digitalRead` 之外就是纯状态机。
2. **第二个显示后端已经跑通**：`font-render-test/framebuffer.hpp` 就是"另一块屏"，只是现在靠"顶替 `TFT_eSPI` 类"实现。
3. **硬约束**：`display.cpp` 头注释写明「无全屏缓冲，按脏区重绘，为 320×240 / 4MB 无 PSRAM 保留 RAM」。
   → 固件**没有整屏帧缓冲**，「把屏幕传出去」**不可能靠 dump 帧缓冲**，只能靠**重放绘制指令**。
   → 320×240×2 = 150 KB/帧，115200 下 ≈ 13 s/帧，位图传输同样不可行。

## 4. 输入适配层（按键）

### 4.1 抽什么

`Buttons` 里只有**一处**硬件读取，把它抽走，状态机就变成纯逻辑：

```cpp
// src/board/levels.h —— 唯一的板级/虚拟差异点
namespace rockey {
class ButtonLevels {
 public:
  static void Init();
  static void Tick(uint32_t nowMs);   // 虚拟源做注入 TTL 过期；GPIO 源为空实现
  static bool IsDown(Btn b);          // 已去极性：true = 按下
};
}
```

三个实现，**编译期单选**：

| 宏 | 实现 | 用于 |
| --- | --- | --- |
| `ROCKEY_INPUT_GPIO` | 引脚表取自 board profile（`kBtnPins[3]`、`kBtnActiveLow`），`INPUT_PULLUP` + `digitalRead` | 真机（Core BASIC / 裸板） |
| `ROCKEY_INPUT_VIRTUAL` | 电平由调试链路注入，**吸收现有 `DevSetLevel` + TTL 语义** | 仿真器 / 远程调试 |
| `ROCKEY_INPUT_HOST` | 主机测试直接设值 | 主机回归 |

### 4.2 收益（这就是"中间层"要买的东西）

| 场景 | 改动量 |
| --- | --- |
| 换主板 | 只改 board profile 的 3 个引脚（+ 极性） |
| 虚拟映射 | 换 `ROCKEY_INPUT_VIRTUAL`，**`Buttons` 去抖/长按/重复/松键栅栏一行不动** |
| 主机测试 | 换 `ROCKEY_INPUT_HOST`，**删掉** `navigation_native.cpp` 里覆盖全局 `digitalRead()` 的写法 |
| 发布固件 | `Buttons` 里不再有 `#if ROCKEY_DEV_BUTTON_API` 分支——**测试注入从状态机里消失**，挪进虚拟源 |

副作用是好的：`buttons.cpp` 不再 `#include <Arduino.h>`，`Buttons` 变成可以单独编译、单独测的纯状态机。

### 4.3 极性语义（必须保留的一条）

真机一律「**内部上拉、按下为低**」。这一条是电气语义，不是实现细节：`Buttons::Init` 里的 `slots_[i].raw = digitalRead(pin) != LOW` 就是这个意思，`IsDown()` 已经把 `!stable` 去极性成"按下"。虚拟源必须**注入同样的语义**，否则去抖/栅栏的行为会与真机不一致——而那正是 `DevSetLevel` 注释里写的「注入原始电平，不直接制造批准」的含义。

### 4.4 安全闸门

`rockey_config.h` 已有互斥模板，扩展即可：

```cpp
#if defined(ROCKEY_BUILD_RELEASE) && (defined(ROCKEY_INPUT_VIRTUAL) || defined(ROCKEY_DEV_CONSOLE))
#error "虚拟输入 / 调试台只能存在于非发布档；不得进入钱包固件"
#endif
```

## 5. 显示适配层（panel）

### 5.1 接口

放在 `src/board/panel.h`，只声明原语，**不含布局、不含字体逻辑**（那些留在 `display.cpp`，保持单一实现）：

```cpp
namespace rockey::panel {

void Init();
int16_t Width();
int16_t Height();
void FillScreen(uint16_t c);
void FillRect(const Rect& r, uint16_t c);
void FrameRect(const Rect& r, uint16_t c);
void Pixel(int16_t x, int16_t y, uint16_t c);

// 语义化原语：让虚拟后端能「只发一次字形位图」，而不是每像素一次
void GlyphDraw(const TableFont* tf, const TableGlyph& g,
               int16_t penX, int16_t lineTop, uint16_t fg, uint16_t bg, const Rect& clip);
void BuiltinChar(uint8_t fontId, int16_t x, int16_t y, uint16_t cp, uint16_t fg, uint16_t bg);

}  // namespace rockey::panel
```

**为什么 `GlyphDraw` 必须是语义原语**：`DrawTableGlyph` 现在是「擦盒 `fillRect` + 逐点亮 `drawPixel`」。按像素序列化，一个汉字 ≈ 上百条 op × 6 B ≈ 600 B；按语义序列化 = 字形引用 + 位置 ≈ 12 B。**差 50 倍**。

**板 profile 不能只有引脚**：profile 还需提供 `PowerOn()` / `PanelReset()` / `SetBacklight(duty)` 三个钩子——Core BASIC 上退化成「GPIO33 拉一下 + GPIO32 PWM」，其它板可能是 I2C 事务。**裸板 + 虚拟屏上这三个钩子都是空实现。**

### 5.2 三个后端

| 后端 | 实现 | 用于 | flash 成本 |
| --- | --- | --- | --- |
| `PanelTft` | TFT_eSPI，驱动宏由面板 profile 决定 | 真机带物理屏 | 仅被选中的那一个驱动 + 实际 `LOAD_FONT*` |
| `PanelVirtual` | 把原语序列化成 op 流写调试链路 | **裸板 / 仿真器 / 远程调试（一等公民）** | 约 1–2 KB，**不链接 TFT_eSPI** |
| `PanelHost` | 内存帧缓冲（复用 `font-render-test/framebuffer.hpp` 的像素逻辑） | 主机回归门禁 | 主机侧，不进固件 |

`PanelHost` 从"伪造 `TFT_eSPI` 类"降级为"实现 `panel` 原语"后，`src/ui/font.cpp` 里的 `#include <TFT_eSPI.h>` 可以彻底消失——**host / virtual 构建不再需要 TFT_eSPI 头**。

**TFT_eSPI 的编译期约束（必须承认）**：`ILI9341_DRIVER` 是宏，`User_Setup.h` 经 `-include` 全局生效，**一个构建只能一个面板驱动**。所以多屏靠 PlatformIO env 区分，不是运行时切换。

## 6. 板 profile

```
src/board/profiles/
  m5stack_core_basic_v27.h   ESP32-D0WDQ6, 屏 ILI9341(GPIO), 键 39/38/37, 背光 32   ← 现有真机，安全验收板
  esp32s3_bare.h             ESP32-S3,     无物理屏,        键 4/5/6,     无背光    ← 新增，仿真 / 远程开发板
```

几何 → 布局参数单独一张表：

```cpp
struct LayoutMetrics { int16_t w, h, headerH, footerH; };
// 目前只定义一套：320×240 → 26 / 30（= 现有 board.h 的取值）
static_assert(kMetrics.h == 240 && kMetrics.w == 320,
              "布局参数尚未为其他几何标定；宁可编译失败，也不要错版面");
```

**刻意的取舍**：`app.cpp` 有 39 处 `Board::` 引用按固定行高排版（菜单 9 项滚动窗口、阅读页裁剪、公钥三行 hex）。其它分辨率要逐屏重排，是独立工作量，不该混在适配层里悄悄发生。

选择方式：`-D ROCKEY_BOARD=...` 指向 profile 头文件，未定义时 `#error`（与 `i18n.cpp` 的既有做法一致，不静默回落）。

### 6.1 新板：ESP32-S3 裸板（建议）

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 芯片 | **ESP32-S3** | esp-emu `--chip esp32s3` 支持；Xtensa LX7 双核，与原 ESP32 同为 Xtensa，Arduino-ESP32 路径最近 |
| 参考实物 | ESP32-S3-DevKitC-1 或任意 ESP32-S3-WROOM-1 裸板 | 便宜、通用、有 USB-Serial-JTAG |
| 屏 | **无物理屏 → `PanelVirtual`** | 屏由我们自己的驱动映射到 Web |
| 键 | **BtnA=GPIO4、BtnB=GPIO5、BtnC=GPIO6**，内部上拉、按下为低 | 避开 strapping（0/3/45/46）、USB（19/20）、flash/PSRAM（26–37） |
| 调试链路 | UART1（引脚经 GPIO 矩阵任意分配） | 对应 esp-emu `--uart1-tcp` |
| 协议链路 | UART0 / USB-Serial-JTAG | 对应 esp-emu `--uart-tcp`（UART0） |

芯片备选（都在 esp-emu 支持列表内）：

| 芯片 | 相对 S3 的取舍 |
| --- | --- |
| `esp32c6` | RISC-V 单核，仿真更简单、风险更低；但与原 ESP32 差异大（CLIC/中断、单核） |
| `esp32c3` | 同上，且 esp-emu 的 UART1 桥在 C3 上**已验证过**（README 明说 C3/P4） |
| `esp32p4` | 双核 HP + PIE SIMD，偏重，不必要 |

**选 S3 的决定性理由是 UART 数量，不是性能。** ESP32-C3 只有 **2 个** UART 控制器（官方文档原文："The ESP32-C3 chip has 2 UART controllers"），S3 有 **3 个**（"The ESP32-S3 chip has 3 UART controllers"）。而本方案需要三口：

| 口 | 用途 | esp-emu |
| --- | --- | --- |
| UART0 | VLP 协议 | `--uart-tcp 127.0.0.1:5555` |
| UART1 | **虚拟屏 + 按键** | `--uart1-tcp 127.0.0.1:5558` |
| UART2 | 日志 | 不桥（真机接第二根 USB-TTL） |

**关键**：esp-emu 只桥 UART0/UART1，所以虚拟屏**必须**落在 UART1 → 日志只能去 UART2 → **C3 上这个分配根本排不出来**，必须改代码或砍日志。

### 6.2 S3 在 esp-emu 上的站立性（本次已实测）

README 只说 `--uart1-tcp` 在 C3/P4 上验证过，所以 S3 + UART1 本来是最大的未知。现已用 **MicroPython 的 S3 镜像**（无需 PlatformIO/工具链）证伪：

```
esp-emu --chip esp32s3 --firmware mp-s3-v1.29.0.bin --uart1-tcp 127.0.0.1:5558 \
        --inject '…u=UART(1,115200,tx=17,rx=18); u.write(b"HELLO-UART1"…)…'
```

结果：ROM → bootloader → 应用全链路走通，宿主侧收到 `b'HELLO-UART1\nTRAILER-OK\n'`。
→ **S3 的 CPU 仿真与 UART1 TCP 桥在本机均可用**，这把“退到 C3”的备选从必需降为可选。

### 6.3 已否决：M5Stack CoreS3（记录理由，避免以后重新讨论）

| 判据 | 结论 |
| --- | --- |
| 芯片 | ESP32-S3 ✓ 在支持列表内 |
| 屏 | ILI9342C 320×240 ✓ 同分辨率 |
| **面板复位** | ✗ **AW9523B I2C 扩展器 0x58 / P1_1**，不是 GPIO → 裸 TFT_eSPI 起不来，要额外写 I2C 上电码 |
| **背光** | ✗ **AXP2101 PMIC 0x34 / DLDO1**（调压，不是 PWM） |
| **驱动支持** | ✗ **TFT_eSPI 没有 ILI9342 驱动**（`TFT_Drivers/` 只有 ILI9341/9481/9486/9488/ST7735/ST7789/ST7796/GC9A01…），只能拿 `ILI9341_DRIVER` 顶 |
| **换料风险** | ✗ 2026-08-07 起新批次屏从 ILI9342C 换成 **ILI9342E**（M5GFX ≥ 0.2.27 才跟得上），TFT_eSPI 侧无保护 |
| 按键 | 无 A/B/C 实体键（触摸 + POWER/RESET）；可自行映射 GPIO，但屏的坑更大 |

→ 结论：**CoreS3 不是我们的目标板。** 裸板 + 自研虚拟屏把上面所有坑一次性绕开，而且更符合"屏是我们自己设计的"这一诉求。

## 7. 虚拟屏协议（op 流）—— 我们自己的"屏幕驱动"

**分层**：`帧(魔数 0xA5 0x5A | ver | type | len | payload | CRC16-CCITT)`，与 VLP 线缆帧**不共用**、**不走同一条串口**（项目已有结论：日志插进帧流会导致主机随机重同步）。

**下行（设备 → 宿主/浏览器）**

| op | 载荷 | 说明 |
| --- | --- | --- |
| `hello` | ver, 面板 W/H, 字库 ID, 板名 | 重连后客户端据此重建画布并请求全量重放 |
| `fillScreen` | color | |
| `fillRect` | x,y,w,h,color | 覆盖 `Fill` / `HLine` / `VLine` / 进度条 / 焦点标记 |
| `frameRect` | x,y,w,h,color | 对应 `Display::Frame` |
| `glyphDef` | role, cp, w,h,xOff,yOff,advance,baseline,bitmap… | 该 (role,cp) 首次出现时下发 |
| `glyphDraw` | role, cp, x, y, fg, bg, clip | 之后只发引用 |
| `clip` / `clipReset` | rect | 对应 `DisplaySetClip` |
| `pong` | — | 心跳 |

**上行（宿主 → 设备）**：`button {btn, down}`、`ping`、`resync`。

**字形从哪来**：`PanelVirtual` 只在 `ROCKEY_FONT_TABLE=1` 构建可用（`#error` 兜底），字形位图取自项目自己的 `gfx_rockey_*`（`src/i18n/fonts/rockey_fonts.h`）。**因此浏览器不需要第二份字体，也不需要复制任何排版逻辑**——它只 blit 设备给的位置。这也意味着「浏览器显示的像素」与「设备会画的像素」由构造决定一致。

**带宽估算**

| 场景 | op 量 | 体积 | 115200 | 921600 |
| --- | --- | --- | --- | --- |
| 满屏纯色 | 1 | 8 B | 瞬间 | 瞬间 |
| 一整屏文字（首次，含 ~40 个字形位图） | ~120 | ~1.5 KB | ~0.13 s | ~16 ms |
| 同一屏重绘（字形已缓存） | ~120 | ~0.7 KB | ~0.06 s | ~8 ms |
| 对照：raw 帧缓冲 | — | 150 KB | ~13 s | ~1.6 s |

结论：**op 流是唯一可用的方案**，且在 115200 下就够做"近似实时"的远程调试。

## 8. 按键注入与安全闸门

- 按下：`down=true, ttl=4000`，之后每 ~1 s 心跳续期（复用 `DevSetLevel` 已有的 TTL 过期保护，掉线自动松开）。
- 松开：`down=false`。
- 长按进度条是设备**重绘**出来的，会自然出现在虚拟屏上，无需额外 op。
- 注入走 §4 的 `ROCKEY_INPUT_VIRTUAL`，**不进入 `Buttons` 内部**。

## 9. Web 调试台（虚拟屏的目的地）

`tools/dev-console/main.py` + `static/`（单页，无框架、无构建步骤）。

**依赖：只用 Python 标准库。** 理由是本机就踩过：`font-render-test/check.py` 因缺 Pillow 至今没跑过。调试台不允许再引入 pip 依赖。

| 端点 | 方向 | 作用 |
| --- | --- | --- |
| `GET /` | → | 静态页：canvas 320×240 + A / B / C 三键（鼠标 + 键盘 `A/S/D`） |
| `GET /events` | SSE | op 流下行（服务端解析协议后转发，浏览器不做协议解析） |
| `POST /button` | ← | `{btn, down}` → 上行按钮帧 |
| `GET /screenshot.png` | ← | **可选**：服务端把当前 op 流重放到内存帧缓冲并出 PNG（离线出图，可直接喂给 golden 检查） |

传输：`--tcp 127.0.0.1:5558`（仿真器）或 `--serial /dev/ttyUSB1 --baud 921600`（真机第二串口）。
服务端保留**一份服务端帧缓冲**，这样"无浏览器也能出图"，也让 §11 的交叉验证门禁成为可能。

## 10. 与 esp-emu 对接

```sh
esp-emu --chip esp32s3 --firmware build/merged.bin \
        --flash-size 8M --psram-size 0 \
        --uart-tcp 127.0.0.1:5555 \     # UART0：VLP 协议（S3 上 ARDUINO_USB_MODE=0 时 Serial=UART0）
        --uart1-tcp 127.0.0.1:5558      # UART1：虚拟屏 + 按键
python3 tools/dev-console/main.py --tcp 127.0.0.1:5558
```

**必须澄清**：esp-emu 是 **SoC 模拟器，不模拟板子，也不模拟任何 LCD 控制器**（外设清单里没有任何面板模型）。
所以"在模拟器里跑起来" = 芯片在支持列表内 + 我们自己的 `PanelVirtual` 把屏画到 Web 上。**不要指望 esp-emu 出屏。**

**已知风险（待验证，不当作已通过）**

| 风险 | 影响 | 验证方式 |
| --- | --- | --- |
| ~~esp-emu 的 UART1 TCP 桥 README 只声明在 C3/P4 上验证过~~ | — | **已实测通过**（§6.2）：S3 引导正常，`--uart1-tcp` 收到固件写入的字节 |

## 13. 附：本次调研发现的既有缺陷

**日志串口名不副实，且从未初始化**（`src/core/log.cpp:24-26`）：

```cpp
#if defined(ROCKEY_LOG_UART2)
  static HardwareSerial s(1);   // ← 构造的是 UART1，不是 UART2
  LogLine(s, line);
#endif
```

三个问题叠在一起：

1. 宏名 `ROCKEY_LOG_UART2`、`log.h:8` 的注释（“日志走 UART2”）、`platformio.ini` 的注释（“TX=GPIO17”）都说是 UART2，代码用的是 `HardwareSerial(1)` = **UART1**。
2. 全仓库只有 `board.cpp:17` 的 `Serial.begin()`；**日志串口没有任何 `begin()`** → 发布档的日志实际发不出去（或发到未配置的引脚）。
3. 若选 C3，这三处注释描述的“UART2” 根本不存在（C3 只有 UART0/1），会直接撞墙。

影响：RK 里与日志口相关的条目需要重新对证；本设计因此**不把“日志占一个 UART”当成已成立的前提**（见 §6.1 的分配表——它是我们新排的，不是继承的）。

**另一条：固件是单线程、无浮点**（`grep` 实测零 `xTaskCreatePinnedToCore` / `xPortGetCoreID` / `float` / `double`；Arduino API 只用到 `millis/Serial/ESP/delay/analogWrite`）。
→ 选 S3 **不是因为**它的双核或 FPU 用得上（用不上），而是因为 UART 与 GPIO 余量。
